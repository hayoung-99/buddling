# tap-tap 기획서

이 문서는 **왜 이 제품인지, 누구를 위한 것인지, 무엇을 성공으로 보는지**를 적습니다.
어떻게 만들었는지는 [README.md](../README.md), 고칠 때 지킬 관례는
[CLAUDE.md](../CLAUDE.md) 에 있습니다. 여기에는 **제품을 판단하는 근거**만 둡니다.

---

## 한 줄

바탕화면 위에 작은 친구를 띄워 두고, **내 캐릭터를 누르면 상대 화면에서 캐릭터가
춤을 추는** 앱입니다.

## 무엇을 해결하나

말을 걸기에는 시시하고, 안 걸자니 아쉬운 순간이 있습니다. "뭐 해?" 라고 보내면
상대가 답해야 할 것 같아서 부담이 되고, 그렇다고 이모지 하나만 보내기도 뻘쭘합니다.
그 사이에 **답할 필요가 없는 신호**가 비어 있습니다.

tap-tap 은 그 자리를 채웁니다. 내가 내 캐릭터를 톡 누르면 상대 화면의 캐릭터가
춤을 춥니다. 받은 쪽은 **아무것도 하지 않아도 됩니다.** 읽음 표시도, 답장해야 할
말풍선도 없습니다. 그냥 화면 구석에서 뭔가 잠깐 움직였고, 그게 나였다는 것만
전해집니다.

**답을 요구하지 않는다는 것이 이 제품의 전부**입니다. 여기에 읽음 표시나 답장
기능을 붙이는 순간 메신저가 되고, 메신저는 이미 충분히 많습니다.

## 누구를 위한 것인가

**친한 사이**입니다. 친구, 커플, 가족, 오래 붙어 지낸 동료처럼 **용건 없이 서로를
건드려도 어색하지 않은 관계**를 봅니다.

정원이 이 판단을 이미 반영하고 있습니다. 한 방에 **최대 5명**, 한 사람이 최대
**3개** 방입니다. 이 숫자는 회사 조직도에는 맞지 않고, 친한 사이에는 넉넉합니다.
30명짜리 부서를 담을 생각이 애초에 없습니다.

**업무용 협업 도구가 아닙니다.** 자리 비움 상태를 관리하거나, 근태를 보여 주거나,
회의를 잡는 쪽으로는 가지 않습니다.

## 무엇을 만드는 것이 목적인가

이 제품의 성공은 **사용자 수가 아니라 완성도**입니다. 목적이 "제품 하나를 앞뒤가
맞게 끝까지 만들어 보는 것" 이기 때문에, 지표는 참고만 하고 판단은 다음 셋으로
합니다.

| | 무엇을 보나 |
|---|---|
| **앞뒤가 맞는가** | 제품이 쓰는 말·화면·기능이 위에 적은 목적과 어긋나지 않는가 |
| **끝까지 갔는가** | "이건 나중에" 로 남겨 둔 구멍이 없는가. 있다면 **일부러 남긴 것**이라고 적혀 있는가 |
| **손이 가는가** | 켜 두고 싶은가. 껐다면 왜 껐는지 설명할 수 있는가 |

어드민 대시보드(`/admin`)의 숫자는 **판단의 근거가 아니라 관찰**입니다. 실제로
쓰이는지 눈으로 보려고 둔 것이지, 이 숫자를 올리는 것이 목표가 아닙니다.

## 지금 있는 것

제품 관점에서 지금 무엇이 되어 있는지입니다. 기술적인 설명은 README 에 있습니다.

### 신호

**하나뿐입니다 — 콕 찌르기.** 내 캐릭터를 클릭하면 그 방 멤버들의 화면에서
캐릭터가 춤추고, 발밑에 누가 찔렀는지 이름표가 붙습니다. 팀 창에서 특정 한 사람만
찌를 수도 있습니다.

받는 쪽이 하는 일은 없습니다. 확인 버튼도, 사라지지 않는 알림도 없습니다.
0.84초짜리 춤이 두 바퀴 돌고 끝납니다.

### 캐릭터

5종(해피 캣 · 터비 독 · 퍼지 판다 · 덤 덕 · 홉 버니)이고 **모델 파일 없이 코드로
그립니다.** 방마다 한 마리씩 뜨고, 방마다 다른 동물을 골라 두면 어느 쪽에서
온 신호인지 한눈에 보입니다.

다섯이 **리그 하나를 공유합니다.** 색·비율·귀 모양·꼬리 모양만 다르게 준 것이라,
어느 하나도 겉돌지 않는 **한 세트**로 보입니다. 이것이 지금 캐릭터의 가장 큰
자산이고, 밖에서 에셋을 가져올 때 가장 먼저 잃는 성질입니다.

대신 **몸이 단순합니다.** 팔은 몸통에 붙은 관절 없는 돌기이고 다리는 발만
있습니다. 그래서 표현할 수 있는 동작의 폭이 좁습니다 — 아래 "앞으로" 참고.

캐릭터·크기·위치는 **내 화면에만 적용되는 개인 설정**입니다. 상대에게 내가 뭘로
보이는지를 내가 정하지 않습니다 — 각자 자기 화면을 꾸밉니다.

### 참여

계정도 비밀번호도 없습니다. 닉네임과 6자리 초대코드만 있으면 됩니다. 초대코드는
**24시간 뒤 만료**되고 언제든 새로 발급할 수 있습니다.

신원은 기기에 붙어 있습니다(익명 로그인). **세션을 잃으면 소속도 잃고**, 돌아오는
길은 초대코드로 다시 들어오는 것뿐입니다.

### 늘 떠 있는 앱이라는 것

컴퓨터를 켠 순간부터 끌 때까지 화면에 있습니다. 그래서 **가만히 있을 때 얼마나
게으르게 구는가**를 사용자가 고를 수 있게 했습니다 (부드럽게 · 균형 · 절약,
캐릭터 3마리에 CPU 약 9% · 5% · 3%). 숨기거나 컴퓨터가 잠들면 아예 그리지
않습니다.

캐릭터 옆 빈 자리는 클릭이 바탕화면으로 통과합니다. **가리지 않는 것**이 늘 떠
있는 앱의 최소 예의입니다.

### 그 밖

- 4개 언어(한국어·English·日本語·中文), 운영체제 설정을 따라갑니다
- macOS · Windows · Linux
- Windows 는 자동 업데이트, macOS 는 새 버전 안내만
- 랜딩페이지(한국어·영어)와 읽기 전용 어드민 대시보드

## 일부러 하지 않은 것

이 목록은 "아직 못 한 것"이 아니라 **"안 하기로 한 것"** 입니다. 여기에 있는 것을
하자는 제안이 나오면, 먼저 이 문서의 목적을 다시 읽어야 합니다.

| 안 하는 것 | 왜 |
|---|---|
| **텍스트 메시지** | 답을 요구하지 않는다는 전제가 무너집니다. 메신저는 이미 많습니다 |
| **읽음 표시 · 알림 뱃지** | 받은 쪽에게 할 일이 생깁니다. 놓쳐도 되는 신호여야 합니다 |
| **소리** | 늘 떠 있는 앱이 소리를 내면 껴야 할 이유가 됩니다 |
| **기록 · 히스토리** | 지나간 것을 되돌아보게 만들면 부담이 생깁니다. 그 순간에만 있는 신호입니다 |
| **로그인 화면** | 계정 만들기가 첫 관문이 되면 대부분 여기서 그만둡니다 |
| **큰 방** | 5명을 넘기면 신호가 소음이 됩니다. 30명이 서로 찌르는 화면은 끄고 싶어집니다 |
| **모바일** | 바탕화면에 있다는 것이 제품의 절반입니다. 폰에는 그 자리가 없습니다 |
| **신호를 종류별로 끄기** | 보내는 쪽의 시그니처를 받는 쪽이 덮으면 뜻이 사라집니다. 끄는 것은 방 단위뿐입니다 |
| **상태를 남에게 보이기** | 자는 중·자리 비움처럼 내 상태를 남이 보게 되면 설명할 일이 생깁니다 |

## 알고 둔 선택

어색해 보이지만 **일부러 그렇게 둔 것**입니다. 고치자는 제안이 나오면 여기를 먼저
읽어야 합니다.

### 방이 없으면 캐릭터도 없다

캐릭터 창은 소속마다 하나씩 만들어집니다(`apps/desktop/src/main/main.ts:86`). 그래서
방이 하나도 없으면 캐릭터가 한 마리도 뜨지 않고, 대신 방을 만들라는 창이 열립니다.

이 때문에 **처음 연 사람은 "바탕화면 위의 작은 친구" 대신 입력 폼을 먼저 만납니다.**
랜딩이 약속한 것과 첫 화면이 어긋나는 자리라는 걸 알고 있습니다.

그래도 그대로 둡니다. 혼자 있는 캐릭터는 **아무것도 하지 않는 캐릭터**이고, 이 앱은
누군가 반대편에 있어야 뜻이 생기기 때문입니다. 혼자서도 쓸 만하게 만들려 들면
다마고치 쪽으로 끌려가는데, 그것은 이 제품이 하려는 일이 아닙니다.

대신 **어긋남은 랜딩에서 미리 맞춥니다** — 둘 이상이어야 시작된다는 것을 받기 전에
알 수 있어야 합니다.

## 지금 어긋나 있는 것

**제품이 쓰는 말이 목적과 맞지 않습니다.**

지금 tap-tap 은 온통 '팀' 이라는 말을 씁니다 — 팀 만들기, 팀원, 팀 목록, 팀 나가기.
랜딩페이지 스크린샷의 예시도 "디자인팀" 이고, 어드민도 팀 단위로 셉니다. 그런데
위에서 정한 대로 이 제품이 보는 것은 **친한 사이**입니다.

이 어긋남은 겉모습 문제가 아닙니다. 받아 본 사람이 **회사에서 쓰는 것**으로 읽으면
쓰는 법 자체가 달라집니다. 근무 시간에만 켜고, 상사가 볼까 봐 안 찌르고, 5명 정원을
보고 "우리 팀은 못 쓰겠네" 라고 판단하고 닫습니다. **정원 숫자가 이상해 보이는
이유가 말이 잘못 걸려 있기 때문**입니다.

범위는 생각보다 작습니다. 사용자에게 보이는 층에만 걸려 있고, 데이터베이스 테이블과
코드 식별자(`teams` · `team_id`)는 그대로 둬도 됩니다.

- 사전 4개(`packages/shared/src/i18n/{ko,en,ja,zh}.json`) — 한국어 30줄 · 일본어 28줄 ·
  중국어 27줄. 영어 29줄은 낱말을 바꾸는 것이 아니라 **섞여 있는 것을 통일**하는 일입니다
  (아래 1단계)
- 랜딩 카피 2개(`apps/web/lib/copy.ko.tsx` · `copy.en.tsx`) — 각 15줄. 페이지 제목과
  설명도 여기 있어서 **검색 결과와 링크 미리보기에 그대로 나갑니다**
- 랜딩 스크린샷의 예시 이름
- README(34줄)와 어드민 화면(`apps/web/components/admin/Dashboard.tsx`, 14줄)의 표현
- **`supabase/schema.sql` 의 기본 방 이름 `'우리 팀'`**(`create_team()`). 이름을 비우고
  만들면 이 값이 그대로 화면에 뜹니다 — 식별자가 아니라 **표시 문자열**이라 아래
  "바꾸지 않습니다" 예외에 들어가지 않고, 한국어가 스키마에 박혀 있다는 점에서도
  사전 원칙과 어긋납니다

## 앞으로

순서는 **정체성을 먼저 맞추고, 그 위에 재미를 얹는 것**입니다. 반대로 하면
'팀원을 콕 찌른다' 는 말 위에 하트를 얹게 되어 어긋남이 더 커집니다.

### 1단계 — 말을 목적에 맞춘다

**'팀' 은 '방' 으로, '팀원' 은 '멤버' 로 부릅니다. 다만 이것은 한국어·일본어·중국어
이야기이고, 영어판은 `team`·`teammate` 를 그대로 씁니다.**

| | 그릇 | 사람 |
|---|---|---|
| 한국어 | 방 | 멤버 |
| 日本語 | ルーム | メンバー |
| 中文 | 房间 | 成员 |
| English | team (그대로) | teammate (그대로) |

'방' 을 고른 이유는 **중립적이면서 누가 들어와 있는지를 안 쪽이 정하게** 두기
때문입니다. '무리'나 '친구들'처럼 친밀함을 제품이 먼저 규정하는 말은 가족이나
오래된 동료에게는 어색해집니다. 6자리 코드로 들어오는 5명짜리 묶음에도 잘 맞습니다.

'멤버' 는 '방원' 이 말이 되지 않아서 고른 짝입니다. 마침 **데이터베이스 테이블
이름이 이미 `members`** 라, 이 변경 뒤에는 화면에 보이는 말과 코드가 처음으로
같아집니다.

#### 영어만 team 으로 두는 것

한동안 이 문서는 영어도 `room` 으로 간다고 적어 두었습니다. 실제로 옮겨 보니
**사람을 가리키는 짝이 무너집니다** — `roommate` 는 같이 사는 사람이라 뜻이 아예
다르고, `room member` 로 풀면 한 낱말이던 자리가 매번 두 낱말이 됩니다. 영어 사전은
지금도 사람을 `teammates` 와 `members` 로 섞어 부르고 있어서, **영어에서 할 일은
낱말을 바꾸는 것이 아니라 `teammate` 로 통일하는 것**입니다.

**대신 치르는 값이 있습니다.** 위에서 적은 어긋남 — 회사에서 쓰는 것으로 읽히는 것 —
이 영어권에서는 그대로 남고, 언어마다 제품이 자기를 부르는 말이 달라집니다. 그래도
억지로 맞춘 영어보다 자연스러운 영어가 낫다고 봤습니다. 영어에서 이 어긋남을 받는
것은 낱말이 아니라 **랜딩 카피의 톤**(아래 "랜딩이 약속하는 것")입니다.

앱·랜딩·사전·어드민이 함께 움직입니다. 한 번에 정리되는 대신 **네 언어를 함께
고쳐야 하고**(하나만 고치면 테스트가 잡습니다), 랜딩 스크린샷과 예시 이름도 다시
만들어야 합니다. **새 예시 이름은 '나오리와 친구들'**(영어판 `Naori & friends`)로,
지금의 "디자인팀"을 대신합니다.

데이터베이스와 코드 식별자는 **바꾸지 않습니다.** `teams` · `team_id` 는 그대로
둡니다 — 마이그레이션 비용만 크고 사용자가 볼 일이 없습니다.

#### 랜딩이 약속하는 것

지금 랜딩은 *"내 캐릭터를 누르면 팀원들 화면에서 캐릭터가 춤을 춰요"* 라고, **동작만
설명하고 왜 쓰는지는 말하지 않습니다.**

앞으로는 **해 보라고 부르는 쪽**으로 갑니다 — *"온라인으로 멤버들을 콕콕
찔러보세요"* 같은 결입니다. 가치를 설명하는 문장보다 이 제품에는 이쪽이 맞습니다.
장난이 목적인 앱의 첫 문장이 점잖으면 그 자체로 어긋납니다.

다만 이 문장 하나로는 **둘 이상이어야 시작된다**는 것이 전해지지 않습니다. 방이 없으면
캐릭터도 없기 때문에(위 "알고 둔 선택"), 이걸 모르고 받은 사람은 빈 화면과 입력 폼을
만납니다. 그래서 **히어로 바로 아래 한 줄이 그것을 받아야 합니다** — 누군가를 불러야
시작되는 앱이라는 것을 받기 전에 알 수 있어야 합니다.

### 2단계 — 움직일 수 있는 폭을 넓힌다

신호를 늘리기 전에 **표현할 수 있는 폭부터 넓혀야 합니다.** 지금 팔은 관절 없는
돌기라 손 흔들기가 잘 읽히지 않고, 드러눕기는 아예 표현되지 않습니다.

처음에는 리그에 관절을 더해야 한다고 봤는데, **세 가지를 실제로 렌더해 놓고 보니
답이 달랐습니다.**

- **팔다리를 늘리면 인형이 피규어가 됩니다.** 다리를 만드는 순간 동글동글함이
  사라지고 키가 커져 같은 창에서 더 작게 보입니다. **비율은 그대로 둡니다.**
- **각도만으로는 손 흔들기가 안 읽힙니다.** 짧은 팔을 회전만 시키면 몸통 옆면을
  따라 올라가 묻힙니다.
- **어깨를 바깥·위로 잠깐 옮기면 읽힙니다.** 비율을 하나도 안 건드리고 팔이
  실루엣 밖으로 나옵니다.

그래서 **리그는 손대지 않고 애니메이션이 쓰는 항목만 늘립니다** — 한쪽 팔만 드는
각도, 그 팔의 어깨를 옮기는 양, 고개와 귀가 떨궈지는 정도. 어깨를 옮기는 것은
동작이 끝나면 제자리로 돌아오는 값이라 다른 동작에는 영향이 없습니다.

**드러눕기는 "녹아내리기" 로 만듭니다.** 캐릭터 창이 세로형이라 진짜로 누우면
가로가 모자라 잘립니다. 대신 제자리에서 무릎이 풀리듯 낮아지고 고개가 떨궈지게
하면, '늘어짐'은 전해지면서 창 크기도 발밑 고정도 건드리지 않습니다.

함께 **동작을 만드는 도구**를 짓습니다. `npm run preview` 화면이 이미 있으니, 거기에
키프레임을 슬라이더로 만지고 곧바로 재생해 보고 **키프레임 배열을 뽑아 주는 것**을
붙입니다. 지금은 `animations.ts` 에 숫자를 손으로 적고 빌드해서 눈으로 확인하는데,
동작이 다섯으로 늘면 그 방식으로는 감당이 되지 않습니다.

### 3단계 — 신호에 성격을 붙인다

지금 신호는 콕 찌르기 하나뿐입니다. 여기에 넷을 더해 **다섯 가지**로 만듭니다.

| 신호 | 뜻 | 비고 |
|---|---|---|
| **콕** (춤추기) | 나 여기 있어 | 지금 있는 것 |
| **폴짝** | 반가움 · 신남 | `hop` 애니메이션이 이미 있습니다 (`npm run preview` 의 '폴짝') |
| **손 흔들기** | 인사 | 콕 과 뜻이 가장 분명하게 갈립니다. 어깨를 옮겨야 읽힙니다 |
| **하트** | 애정 · 고마움 | 음표 대신 하트가 떠오릅니다 |
| **드러눕기** | 심심함 · 늘어짐 | 눕히지 않고 제자리에서 무너지게 합니다 (2단계 참고) |

**고르는 방식이 이 단계의 핵심입니다.** 신호를 메뉴에서 고르게 하면 캐릭터를 톡
누르는 0.2초짜리 동작이 사라집니다. 그래서 **누르는 동작은 그대로 하나로 두고**,
평소에 나갈 신호를 **미리 골라 둡니다.**

그 결과 신호는 표현의 목록이 아니라 **사람의 시그니처**가 됩니다. "쟤는 늘 하트를
보내" 같은 것이 생깁니다. 표현을 넓히는 일이라기보다 **캐릭터에 성격을 붙이는
일**에 가깝고, 그 편이 이 제품에 맞습니다.

골라 둔 신호는 **방마다 따로**입니다. 캐릭터·크기·위치가 이미 방마다 따로 저장되는
개인 설정이라 그 결을 그대로 따릅니다. 가족 방과 친구 방에서 다르게 굴 수 있습니다.

#### 한꺼번에 오면

| 상황 | 어떻게 |
|---|---|
| 재생 중인 것과 **같은 신호** | 먼저 온 것을 계속 재생합니다 (지금과 같습니다) |
| 재생 중인 것과 **다른 신호** | **재생 도중이라도 곧바로 새 신호로 바뀝니다** |
| 이름표 | **신호 종류와 상관없이 전부** 발밑에 붙습니다 |

**늘 마지막에 온 신호가 화면에 있습니다.** 사람마다 골라 둔 신호가 그 사람의
시그니처인데, 앞사람 동작이 끝나기를 기다리면 방금 보낸 사람의 것이 늦게 나타납니다.
다섯 가지를 한꺼번에 겹쳐 재생하지 않는 이유도 같습니다 — 그러면 무엇 하나 안
읽힙니다.

#### 잠재우기

받는 쪽이 쓸 수 있는 것은 **방 단위 잠재우기 하나**입니다. 신호 종류를 골라서 끄지는
못합니다 — 보내는 사람의 시그니처를 받는 쪽이 덮어쓰면 그 의미가 통째로 사라지기
때문입니다.

잠재운 방의 캐릭터는 **웅크려 자는 모습**이 됩니다. 껐다는 사실을 목록 어딘가의
토글이 아니라 **화면에 보이는 그림**이 알려 주므로, 껐다는 것을 잊고 "왜 아무도
안 찌르지" 하는 일이 생기지 않습니다.

**자는 모습은 내 화면에만 보입니다.** 방의 다른 멤버에게는 평소와 똑같이 보이고,
그들은 평소처럼 보냅니다. 상태를 남에게 보이기 시작하면 "왜 자고 있어?" 라고 물을
자리가 생기고, 그것은 이 제품이 없애려던 부담입니다.

#### 옛 버전과의 호환

지금 프로토콜은 '찔렀다' 하나입니다. 신호 종류를 실어 보내면 **업데이트하지 않은
상대는 모르는 값을 받습니다.** 이때는 **기본 춤으로 떨어뜨립니다** — 뜻이 조금
어긋나는 편이 아무 일도 일어나지 않는 것보다 낫습니다.

### 먼 목표 — Blender 로 5종을 직접 만든다

**언젠가는 캐릭터를 코드 생성에서 3D 모델 파일로 옮깁니다.** README 와
`characters.ts` 주석이 "모델 파일이 하나도 없다" 를 자랑처럼 적어 두고 있지만,
그것은 **지금의 구현 선택이지 지켜야 할 원칙이 아닙니다.** 이 문서를 근거로
읽어 주세요.

**다만 지금은 아닙니다.** 위 2단계로 몸을 늘리면 손 흔들기도 드러눕기도 표현되므로,
당장의 병목은 옮기지 않고도 풀립니다. 옮기는 것은 **표현의 천장을 더 높이고 3D
파이프라인을 직접 다뤄 보는 일**이지, 지금 막힌 것을 뚫는 일이 아닙니다.

옮길 때는 **직접 Blender 로 만드는 길 하나뿐**입니다. 조사해 본 결과입니다.

| 길 | 왜 안 되나 |
|---|---|
| 무료 CC0 팩 (Quaternius 등) | 네발짐승이고 동작이 게임용(Attack · Death · Gallop)입니다. 고양이·판다·오리·토끼가 아예 없고, 무엇보다 **한 세트라는 느낌을 다시 만들 수 없습니다** |
| AI 생성 | 리깅까지 되는 것은 Meshy 뿐인데 무료 등급은 CC BY 4.0 이라 **앱에 저작자 표시**가 필요합니다. 그리고 다섯 번 생성하면 다섯 가지 화풍이 나옵니다 |

옮기는 날 함께 무너지는 것들을 미리 적어 둡니다.

- **아이콘과 랜딩 그림이 같은 캐릭터 코드에서 나옵니다.** 그 스크립트들도 모델을
  읽게 만들지 않으면 캐릭터가 세 군데서 따로 놉니다
- **동작의 합성이 공짜가 아니게 됩니다.** 지금은 겹이 곱해지고 더해져 춤과 움찔이
  동시에 일어나도 서로를 지우지 않는데, glTF 클립으로 가면 `AnimationMixer` 위에서
  그 성질을 다시 만들어야 합니다
- **절전 수치를 다시 재야 합니다.** 스킨드 메시는 매 프레임 CPU 를 씁니다
- **브라우저 없이 도는 테스트가 상당량 무의미해집니다** (`critter.test.ts` ·
  `animations.test.ts`)

### 당분간 하지 않는 것 — 코드 서명

macOS 코드 서명이 없어서 처음 열 때 경고가 뜨고, 그래서 macOS 자동 업데이트도
구조적으로 불가능합니다. 안내 문구로 넘기고 있습니다.

고치려면 Apple 개발자 계정(연 $99)이 필요합니다. **목적이 "만드는 과정"인 지금은
돈을 쓸 자리가 아니라고 봅니다.** 남에게 널리 나눠 줄 일이 생기면 그때 다시 봅니다.

## 정해야 할 것

지금은 없습니다. 위에서 정한 것을 실제 문구와 코드로 옮기는 일만 남았습니다.

**어떻게 잘라 올릴지**는 이렇게 봅니다. 사전 4개·랜딩·스크린샷이 한 덩어리로 움직여서
한 PR 에 다 담으면 커지고, 아무렇게나 나누면 중간 상태에서 말이 섞입니다.

| PR | 무엇 |
|---|---|
| 1 | 사전 4개 + 앱 화면의 말 ('팀'→방, '팀원'→멤버 / 영어는 `teammate` 로 통일) |
| 2 | 랜딩 카피 · 스크린샷 · 예시 이름('나오리와 친구들') · 어드민 화면의 말 |
| 3 | 애니메이션 항목 늘리기 (한쪽 팔 들기·어깨 옮기기·고개 떨구기) |
| 4 | `preview` 를 키프레임 편집기로 |
| 5~ | 신호 하나당 PR 하나 — 폴짝 → 손 흔들기 → 하트 → 드러눕기 |
| | 잠재우기와 자는 모습은 신호가 둘 이상이 된 뒤에 |

**항목 늘리기와 편집기가 신호보다 앞**인 것은 손 흔들기·드러눕기가 그것 없이는
표현되지 않기 때문입니다. 신호 중에서는 **폴짝을 먼저** 두는데, 애니메이션이 이미 있어
프로토콜에 신호 종류를 싣는 일만 검증하면 되기 때문입니다. **드러눕기를 마지막**에
두는 것은 새 포즈라 발밑 고정 규칙을 건드릴 수 있기 때문입니다.
